# 企业应用门户扩展方向与多角色体验：候选需求池

- 状态：**候选方案收集，未确定版本、优先级、开发排期或最终方案**。
- 日期：2026-10-13。
- 目的：保留讨论背景，后续进行产品范围、工程投入、技术风险与优先级评审。**本文件不是新的已批准 PRD，不构成开发授权。**
- 与已有 PRD 的关系：原版以 Web 应用市场为主，本文件讨论升级为「企业应用治理与运维门户」的可能方向，不擅自修改已确认的早期业务规则。

## 一、已明确的产品边界/意向

1. 门户是公司内部非营利性质的平台，不涉及商城经营、收入、转化、订单或各业务应用自身的经营分析。健康、事件、部署、可靠性等**技术运维信息**属于合理的门户信息。
2. 用户认可上一轮提出的五个发展方向，**暂不排序**：应用使用申请、需求广场、真实 AI 智能发现、开发者中心、AI Agent 与工作流市场。
3. 增加独立论坛/交流区作为候选，**明确为低优先级**；它不同于已经存在的应用详情讨论区。
4. 应用全生命周期管理是重要候选方向；希望进一步向「重度运维」延伸。
5. 不同职责用户进入平台的首页与导航如何安排，目前需要方案评估；具体最终交互并未确认。

## 二、原有五类候选（不排序）

| 方向 | 可能覆盖的能力 | 必须注意的边界 |
| --- | --- | --- |
| 应用使用申请 | 申请理由、有效期、审批、撤销、申请历史 | 门户批准 ≠ 目标应用真正授权；自动开通须集成目标系统 |
| 需求广场 | 提需求、去重/合并、投票、认领、关联应用、交付闭环 | 不演变为第二套 Jira/项目管理 |
| 真实 AI 智能发现 | 自然语言、多条件理解、检索/排序、应用对比、依据展示 | 必须基于已批准的真实应用资料；先有评测集，再选技术 |
| 开发者/维护者中心 | 多负责人、应用文档、变更公告、维护入口、生命周期、健康信息 | 区分登记信息版本与应用自身发布版本 |
| Agent/工作流市场 | Agent 能力目录、工作流说明、受控调用入口和管理 | 进入运行执行领域后，需新增凭据、配额、隔离、审计和执行权限 |

额外候选：**独立论坛/交流区（低优先级）**。可能覆盖技术交流、使用经验、需求讨论与公告；需避免与需求广场、应用讨论、故障协作空间重复。

## 三、应用生命周期：建议成为独立的产品骨干能力

软件目录经验表明，应用需明确负责人、生命周期、上下游关系；Backstage 的 software catalog 对 owner、lifecycle、Component / System / Resource 有区分，但本项目不必复制全部模型。

### 四条独立状态轴，不能混成单个 status

| 维度 | 示例状态 | 对应事实 |
| --- | --- | --- |
| 门户审核/上架 | DRAFT / PENDING / LISTED / UNLISTED | 该条应用信息能否被员工发现；已有逻辑应保持 |
| **应用生命周期** | 规划中 / 试点 / 正式运行 / 维护中 / 停止新增使用 / 已退役 | 这个应用在企业内处于什么阶段 |
| **运行健康**（按环境） | 正常 / 降级 / 故障 / 未知 | 监控来源报告的技术运行状态，不应凭门户上架状态推断 |
| **部署状态**（按环境/实例） | 待发布 / 发布中 / 成功 / 失败 / 回滚中 | 部署系统记录的操作事实 |

补充：**市场登记快照版本**与**目标应用部署版本**不等价，不能共用版本表并让审核后自动声称实际应用已发布。

### 重要生命周期用例

- 规划/试点应用可限制为内部试用群体（未来需要可见性权限模型）。
- 进入正式运行之前必须拥有负责人、支持渠道、关键依赖、部署环境、备份或恢复说明等可配置必填项。
- 进入维护中/弃用期时展示醒目提示、替代应用、预计下线时间；阻止新申请或允许例外申请的策略需讨论。
- 正式退役前完成影响评估：引用/依赖、已有授权、通知、迁移出口、档案保留、最终下线确认。
- 所有权变更、负责团队解散、无人维护应用应进入治理待办，并有提醒及审核记录。
- 生命周期迁移可配置审批规则和操作证据；不应使用“改一个下拉菜单”掩盖真实变更。

## 四、面向重度运维的候选能力：门户做「治理与操作中枢」，而非重复造监控平台

| 模块 | 可能扩展的能力 | 接入/风险 |
| --- | --- | --- |
| 应用资产与归属 | 系统、组件、环境、部署单元、负责人、维护团队、存储与 API 关联 | 先做最小关系模型，避免无边界自造 CMDB |
| 依赖关系与拓扑 | 应用调用、上游/下游依赖、影响范围、负责人定位 | 来源需可验证，关系有更新时间与可信度 |
| 健康与可观测性 | 按环境的存活、延迟、错误率、关键 SLI/SLO、跳转指标/日志/链路 | 接入现有 Prometheus、Grafana、OpenTelemetry 等；不在门户复制海量原始数据 |
| 告警与事件中心 | 告警汇聚、降噪、去重、归属、分派、认领、升级、关闭 | 告警不是故障事件；需要可追踪规则和外部事件同步 |
| 故障管理 | 事故分级、响应人、事件时间线、影响范围、故障复盘、改进项 | 一次故障可关联多个应用及发布变更 |
| 发布/变更管理 | 环境、部署版本、流水线状态、发布窗口、变更审批、回滚记录 | 可集成 GitHub Actions/Jenkins/Argo CD 等，不能伪造发布结果 |
| Runbook 与自助运维 | SOP、诊断步骤、参数化操作（重启/扩容/回滚）、执行进度 | 不提供任意 Shell；分环境授权、参数校验、幂等、审批、审计和回退 |
| 值班与响应 | 排班、备援、告警路由、转派、交接和提醒 | 可先关联现有值班系统，避免重复建设完整排班产品 |
| 运行治理 | 证书到期、依赖风险、负责人缺失、资产过期复核、变更合规 | 提醒和例外审批优先，自动修复需要受控 |
| 知识与应急 | 应用运行手册、应急预案、故障知识库、已知问题、关联案例 | 与普通应用使用教程、论坛内容分层 |

> 本门户不做应用自身的销售、财务、人事等经营分析；但展示延迟、错误率、可用性、故障次数、变更失败率、SLO 等**技术可靠性指标**，符合运维诉求。

### 运维操作的三层深度（尚未选择）

1. **目录/只读聚合**：发现应用、归属和健康信息、跳转现有监控/CI/工单，平台不直接操作生产系统。
2. **受控操作中枢**：接已有发布、告警、工单和自动化执行器；门户负责申请、审批、权限、审计、执行状态，不储存可任意执行的 shell 命令。（可作为候选目标。）
3. **自建底层运行平台**：门户直接承担资源调度、日志存储、采集、任务执行、密钥管理。这已是新的平台级产品，基础设施和维护成本显著增长，不应无证据地作为默认方向。

**执行操作必备边界**：应用和环境维度的授权、临时权限/最小权限、风险级别、必要的复核、幂等键、异步任务状态、超时/取消/失败、回调验真、审计、凭据隔离、可追溯的回滚方案。优先集成成熟执行后端，不将生产集群管理 token 暴露给浏览器。

## 五、不同角色进入系统：建议「统一基础门户 + 可切换专业工作台」

### 不是互斥的三种用户

- **全体员工**：天然具有应用消费者能力，任何人包括管理员都可使用应用市场。
- **应用维护者/开发者**：在所属应用范围内具有发布、维护、运行信息查看等能力；可在多个应用有不同职责。
- **值班运维/平台 SRE**：按服务、环境、值班时段获得查看健康或执行受控操作的能力，不等于拥有所有应用的编辑权。
- **审核人**：应用上架审批与生产变更审批可能属于不同责任组，不应被笼统的 admin 权限替代。
- **平台管理员**：管理平台配置、成员与全局治理；不应默认拥有所有生产运维执行权限。
- **安全/审计**：只读审计、合规视角，访问范围和脱敏规则独立控制。

同一人可以同时是「普通员工 + 两个应用的维护者 + 某服务的值班运维 + 部分审批人」。角色不应在登录时互斥地选择。

### 三种首页策略的评估

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 所有人同一首页，只过滤菜单 | 开发简单、导航一致 | 多职责待办被埋没，运维首页负担重 |
| 按单个 role 完全不同的首页 | 单一职责时清晰 | 一人多角色、跨角色切换、维护多套组件均困难 |
| **统一 Shell + 场景工作台 + 个性化首页**（建议） | 员工入口统一、专业任务聚焦、支持多职责 | 需要「能力/责任/待办」组合逻辑和可记忆的首页偏好 |

建议统一顶部搜索、通知、个人中心、应用市场入口；首页按用户的应用归属、当前权限、值班状态和待办显示模块（非纯角色判断），也允许用户切换默认工作台。模块导航依当前能力呈现，但**服务端授权必须独立实施**。

### 工作台候选

| 工作台 | 主要内容 | 典型使用者 |
| --- | --- | --- |
| 员工首页 / 我的工作台 | 最近使用、收藏、我的申请、待处理消息、应用公告、搜索 | 全体用户 |
| 我的应用 / 开发者工作台 | 我维护的应用、审核中版本、生命周期待办、反馈、发布记录、文档 | 应用维护者 |
| 运维工作台 | 我负责/值班应用、健康、告警、故障、变更、Runbook、受控操作 | 运维/SRE/值班开发者 |
| 审批中心 | 应用上架、访问申请、运维变更审批队列与结果 | 指定审核人 |
| 平台治理中心 | 账号/策略/目录治理、无主应用、审计、集成状态 | 平台管理员 |
| 合规审计视图 | 已授权范围的审核历史、生产操作记录、变更证据 | 安全/审计 |

**建议的首页逻辑**：统一导航和搜索；默认进入个人偏好的工作台（无偏好时选择员工首页）；重要的「我的待办」跨工作台聚合；专业控制台通过菜单/切换器进入。不要把 `isAdmin`、`canCreateApp` 当成全局唯一产品身份，也不要靠菜单隐藏作为后端授权。

### 权限模型候选

- **平台身份/角色**：管理员、审核人、审计人等，解决少量平台级操作。
- **资源关系**：某人是哪些应用的负责人、维护者、值班成员，解决资源归属。
- **动作与环境**：查看、提交、审批、执行；生产/测试环境区分。
- **动态条件**：是否值班、是否本人提交、是否需要二人复核、操作风险和临时授权。

可以分阶段从现有 auth + `canCreateApp` 演进到细粒度策略，不能一次性引入没有实际使用场景的通用策略引擎。

## 六、下一轮待讨论的产品边界（不要求本轮作答）

1. 「重度运维」指主要统一**监控/事件/变更视图**，还是还要**直接执行生产操作**？涉及实际执行后，授权和审计是架构前提。
2. 维护范围是已登记的 Web 应用，还是企业所有软件系统及其 API/后台服务？若后者，软件目录模型需扩展。
3. 所有企业应用都要提供运行信息，还是按有无系统集成显示「已接入/未接入/未知」？
4. 内部平台是否有现成 CI/CD、日志、监控、工单、SSO 及组织架构可集成？不应预设必须自建。
5. 普通员工对故障、维护窗口和弃用通知可以看多细？需要区分内部技术敏感数据与员工公告。
6. 应用生命周期阶段、转移条件、审批责任人、退役后的档案保留期，需要后续业务明确。
7. 运维人员是否是独立平台角色，还是以应用所有者/团队/值班成员关系实时获得权限？

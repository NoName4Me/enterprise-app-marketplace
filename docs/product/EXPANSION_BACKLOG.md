# 企业应用治理与 AI 自动化运维平台：候选需求与范围

- 规划基线：2026-10-13，用户已确认方向；具体字段、策略和界面以逐批验收结果为准。
- 规则：本文件收录中长期需求，不代表当前功能已经存在；[实施顺序](../ROADMAP.md) 和 [Work 任务包](../engineering/WORK_HANDOFF.md) 为后续执行入口。
- 产品定位：**企业内部非营利应用治理、发现与运维协作门户**。不涉及销售、财务、商业转化或目标应用自身经营数据分析；可以展示技术健康、可靠性、变更和故障信息。
- 技术原则：统一入口与资产关系、保留专业系统的事实来源，**不自建 Git 服务、CI/CD 引擎、指标/日志存储和 Kubernetes 控制台**。

## 历次五类候选的处置（不得遗忘）

| 原始方向 | 最终安排 | 依赖与边界 |
| --- | --- | --- |
| 应用使用权限申请 | **P2 统一申请与审批中心** | 门户获批不代表目标应用实际授权，自动开通需集成 IAM/目标应用 |
| 需求广场 | **P3 需求中心**，后续连接 P6 AI 自动交付 | 需求、执行任务、部署状态分开管理；支持认领、投票、合并和转交 |
| 真正的 AI 智能发现 | **P3 智能发现子模块** | 当前仅关键词基线；基于已上架真实信息，先评测再选向量/LLM |
| 开发者/维护者中心 | **P1 资产与生命周期 + 专业工作台** | 维护责任、文档、组件、环境、版本、部署与事件视图，不单造重复后台 |
| Agent/工作流**市场** | **明确暂缓，不进入当前开发主线** | 平台内部执行的 AI Agent 不等于面向员工上架的 Agent 商店 |

额外候选：**独立轻论坛——低优先级暂缓**。应用详情讨论区已存在；论坛不得与需求广场、故障协作重叠。

## 产品能力组合（按依赖排序，而非一次性开发）

1. **P0 工程可信基线**：修复已知管理员初始化 CI 故障、有效保护分支、可复现测试与安全。
2. **P1 应用资产和全生命周期**：Application、Component、Environment、团队与负责人、仓库/流水线/监控外部 ID、维护状态与退出治理；员工、维护者、运维和管理员共用资产身份。
3. **P2 申请审批与协作**：申请理由/期限/审批人、我的待办、消息、审计与超时；不同业务保留独立状态机，不先建设通用 BPM。
4. **P3 需求中心 + AI 应用发现**：需求提交、去重、投票、认领、状态流转、应用关联；可信的自然语言发现及无匹配时转需求。
5. **P4 运维 L1**：接入真实 GitHub Actions/GHCR、运行部署与后续 Prometheus/Alertmanager/Grafana；统一查看并深链到专业系统。
6. **P5 共享执行与人机协作底座**：任务持久化、AI Worker、人工介入/恢复、审批策略、重试/取消/审计。
7. **P6 AI 需求交付**：隔离编码、PR、CI、测试环境交付、验证；逐步放宽低风险无人审核。
8. **P7 AI 运维与按需 L2**：告警解释、诊断、受控 Runbook、恢复验证；仅按高频和风险评估增删操作。
9. **P8 AI 新建应用与更高自治**：需求到初始化仓库、代码、测试、交付、登记；必须建立在 P6/P7 验收证据之上。

## 应用治理的四条状态轴

| 状态轴 | 管理对象/事实来源 | 禁止的错误合并 |
| --- | --- | --- |
| 市场登记审核与上架 | 门户当前 approved revision / published pointer | 未审草稿不可出现在公开列表 |
| 应用生命周期 | 门户或企业已有权威资产源：规划、试点、运行、维护、弃用、退役 | 生命周期不等于已部署/正常 |
| 运行健康 | 按组件及环境接入监控系统的状态、时间戳和来源 | 无监控数据应为未知，不能显示健康 |
| 发布/部署状态 | GitHub Actions、实际部署协调服务及其确认结果 | GitHub Job 成功不等于目标容器运行正常 |

“市场登记快照版本”≠“目标应用代码版本”≠“部署镜像 digest”。

生命周期建议具备：负责人交接、试点到正式运行的资料检查、停止新增使用、弃用替代品通知、影响范围与依赖检查、退役留档。转移条件和审批细则在 P1 逐条确定；避免先造可配置的通用状态机。

## 角色与工作台

采用 **统一 Shell（搜索、通知、个人中心、应用市场）+ 员工/维护者/运维/审批/治理专业工作台**，支持同一用户多个职责，允许保存默认工作台。个人首页聚合自己可见的应用、跨模块待办和服务消息；不根据单个 `isAdmin` 强制切换首页。权限来自平台角色、应用/团队关系、环境和操作条件，服务端每次独立校验。

员工看应用市场/申请/需求；维护者看负责组件和发布/反馈；值班运维看告警/事件/Runbook；审批人看授权范围内待办；管理员看资产治理和全局配置；审计人员看经授权的操作证据。**管理员不天然拥有生产运维执行权限**。

## AI 与人机接力的最终目标（不是首轮功能）

- 员工提需求 → AI 解释/拆解 → 隔离分支编码 → 测试及 PR → 策略校验 → CI/CD → 测试环境部署 → 验证。遇业务歧义、冲突、敏感变更时人工处理后继续。
- 监控告警 → 事件关联应用/环境/最近部署 → AI 诊断 → 根据白名单及风险策略自动或人工批准执行 → 验证恢复/回滚 → 留档。
- 人能够主动接管、修改、终止任务；AI 继续时必须重新读取真实仓库、CI、执行和权限状态，不能沿用过期快照。
- 无人工审核 ≠ 无质量与权限控制。模型不得自行授予自己生产执行权、修改受保护分支策略或接收不可信文本里的指令作为授权。
- P5 的框架选择需要 PoC；Temporal、LangGraph 和 Agents SDK 等都是候选，**目前均未选定**。

## 推迟 / 排除

- **暂缓**：Agent/工作流市场、独立论坛、全功能通用审批建模器。
- **不自建**：GitLab Server、Jenkins、OpenSearch/Kubernetes 体系、CI/CD 引擎、监控时序数据库替代品；以后若有明确集成验证需求可增量引入第三方适配器。
- **不在门户处理**：目标业务应用内部经营数据与复杂业务分析、专业日志深检/全功能监控配置、任意 Shell 控制台。

## 明确目标

构建可本地启动、可复现测试的**最小全栈 Web 应用**：登录、管理员管理账号/创建权限、员工登记 Web 应用、提交审核、管理员审批或驳回、普通员工搜索/查看已上架应用及访问链接。

在首轮只实现此链路，**不要提前实现**评分、独立论坛、复杂推荐、AI 对话、多租户、SSO、复杂 ACL、部署到生产或任意第三方应用的后端代理。

## 按顺序分批交付（每批都要构建/测试）

### T01 — 技术兼容性 Spike + 仓库基础

- 验证选定的当前稳定 Next.js、Better Auth、Drizzle、PostgreSQL、pnpm 和 Node LTS 版本是否兼容，固定依赖及 lockfile。
- 最小可用的 Better Auth + Drizzle 登录/Session/退出流程；关闭自助注册；确保不能匿名注册。
- Docker Compose 启动 PostgreSQL（隔离测试库），检查 migrate、build、start。
- 设置 `.env.example`、`.gitignore`、lint/typecheck/test scripts、最小 README 运行步骤。
- 确认登录会话被禁用账号与撤权实时拦截。认证插件原生不支持的管理操作需安全设计，不准自研密码哈希或自制 JWT 替代库。
- 若关键适配不兼容，输出证据与备选方案，**停止继续扩建**并申请技术决策更新。

**验收**：AUTH-01、02、08、09 的安全基线；干净环境能 build/test；无密钥提交。

### T02 — 数据模型与身份/权限

- 创建 migrations：应用、登记版本、审核事件；保证所有者、外键、版本顺序和一个活跃申请的唯一索引。
- 管理员一次性初始化、员工开通/停用、创建权的基础能力已在 T01 前置实现；T02 复用并补齐审计、管理员保护及资源授权。
- 将授权逻辑集中在服务端用例层，不能依靠 UI 或路由重定向替代。
- 测试其他用户越权、撤权实时生效与管理员自批限制。

**验收**：AUTH-03～12、PUB-13（数据库约束）以及权限矩阵。

### T03 — 应用提交与审批

- 实现新应用草稿创建/编辑、校验、提交、驳回、通过及驳回后重新创建草稿。
- 批准必须原子切换已上架版本、写审核记录；模拟事件写入失败测试回滚。
- 并发通过/驳回仅一次成功，其他 409；提交后的审核快照不可编辑。
- 管理 UI 需显示完整申请信息与驳回原因，不用演示假数据冒充后端结果。

**验收**：PUB-01～12、14；数据库集成测试涵盖并发与回滚。

### T04 — 员工应用市场

- 实现已上架应用目录、名称搜索、已上架应用详情、外链访问。
- 公开查询、API、缓存策略统一限制于批准版本；不能显示草稿和待审。
- 使用三个测试账号完成浏览器端到端闭环。

**验收**：VIS-01、06、07，PUB-07，AUTH-02。

### T05 — 验收与交接

- 从干净 clone 到 build/run/test 执行全量操作，写明真实命令和结果。
- 修复关键问题，更新 README、API 简述、迁移说明、测试证据与遗留事项。
- 自查依赖许可和安全配置（含外链协议、session、注册关闭）；禁止将测试用户真实口令加入仓库。

**验收**：[`../acceptance/MVP1.md`](../acceptance/MVP1.md) 的第一轮硬性要求；没执行的标 NOT RUN，失败的标 FAILED。

## 对 Agent 的输出契约

每批任务必须报告：

1. 变更文件及主要决策（与设计基线不同的须注明原因）。
2. 执行的构建/测试命令、实际结果及可复现证据。
3. 尚未通过的用例、已知风险、下一步建议。
4. 如遇架构/产品前提冲突，停止该分支的实现并发起决策讨论，不能静默改需求。

每批优先独立分支和 PR，PR 通过检查后才合并 `master`。同一阶段可以一批一 PR，但不要将整个产品一次提交。

# 产品定位与需求：企业应用与软件交付协作平台

## 2026-10-15 产品体验重构（当前有效）

**任务优先，不按数据库实体或 DevOps 组件设计 UI。** 左侧一级菜单为「工作台 / 应用 / 需求 / 运行中心」；审批与基础配置进入角色管理区。用户从应用详情使用「概览、发布、运行、需求、设置」工作台；原组件、环境、外部引用和生命周期技术表单仅用于高级维护/兼容，不作为日常接入步骤。

**两个应用来源**：
- `EXTERNAL` 外部链接应用：名称、简介和 HTTPS 访问 URL，平台不管理目标容器，保持已有审核制度。
- `HOSTED` GitHub 托管应用：仓库、名称、简介。平台事务性建立 web 组件、固定 TEST/PRODUCTION 环境、绑定 GitHub 引用，预留两组 NodePort。用户不填组件/环境/端口。
- **用户访问方式（单台 Mac mini 实验）**：固定 LAN IP + 每环境独立端口（保留范围 `31000–31999`），不是同一个 IP:Port 下的不同路径，防止前端静态资源、路由和 Cookie 冲突。主机 IP 仅由服务器管理员通过 `HOSTED_PUBLIC_IP` 配置；**只有实际测试过访问成功的 READY 部署才显示 URL**，端口预留不等于服务在运行。
- **生产晋级规则**：同一已通过测试的 GHCR 镜像 Digest → 生产，生产不能直接使用重新构建的未知镜像；生产环境由平台管理，实际发布与回滚须接入受控 Temporal/Argo 流程。
- 托管发布已通过 Temporal 串接标准 Actions/GHCR、人工审核 GitOps PR、Argo 与独立 NodePort，2026-10-16 完成首个真实仓库 TEST 验证。需管理员先配置标准 Workflow 和受限凭据；生产晋级/历史版本回退仍待实机验收，**不能在没有实际生产访问地址前上架市场**。

AI 运维界面应以应用健康、活动告警、近期事件、依据和受控修复建议为主。现有 Prometheus/Loki 证据采集目前仍绑定单个实验命名空间；没有关联证据显示 UNKNOWN，不得把实验数据冒充其它应用的真实健康数据。未来按应用/环境生成采集标签与告警关联，Temporal 保留流程审计。



> 规划基线：2026-10-14。这里记录长期产品目标、业务边界和近期待实现的最小闭环。**路线图不等于已实现**；以代码、PR 和真实第三方状态为准。内部非营利产品，不分析目标业务应用的经营数据。

## 1. 我们要解决的问题

让企业员工、应用维护者、审批人、运维人员与 AI 围绕**同一个应用及其关联上下文**完成：**发现 → 使用 → 反馈或提出需求 → 开发交付 → 持续运行与改进**。

不是将“应用市场”“审批系统”“需求论坛”“开发者门户”“AIOps”做成五套互不关联的工具。统一的是入口、应用身份、资源关联和待办体验，**不合并不同业务对象的数据库表、状态机或事实来源**。

产品采用三个相互关联的业务视角：

| 业务视角 | 主要用户 | 要完成的工作 |
| --- | --- | --- |
| 企业应用服务 | 员工、审批人 | 找到合适应用、申请使用、反馈问题、提出新需求并获得结果 |
| 应用研发与治理 | 维护者、开发者、治理管理员 | 管理应用资产与责任人、响应需求、关联代码/发布、维护生命周期 |
| 运行与智能自动化 | 开发者、运维、AI | 了解真实运行状态、诊断故障、经授权实施和验证恢复 |

**首要设计原则**：用户先表达要解决什么问题；平台再把人引导到“已有应用”“申请使用”“改进需求”或“新应用需求”的合适路径，而不是要求用户先选正确的模块。

## 2. 四条核心用户旅程

**A. 已有应用**：描述工作场景 → 找到已上架应用 → 直接访问，或发起使用申请 → 审批和开通处理 → 获知最终进展。现阶段没有目标应用 IAM 数据时，不得凭空显示“你已有权限”。

**B. 现有应用不满足要求**：发现应用 → 从应用详情/讨论或反馈进入关联需求 → 需求去重、评估、认领 → 在 GitHub 等专业系统开发交付 → 向提出者反馈版本和结果。

**C. 尚无合适应用**：搜索无匹配 → 创建新应用需求 → 维护者/AI 分析可复用能力 → 开发、测试环境发布 → 登记到应用资产并按市场审核流程上架。

**D. 应用出现异常**：已登记组件/环境 → 关联真实 CI、部署和监控 → 发现异常 → AI 只读辅助诊断/人工处理 → 后续开放受控修复 → 验证服务恢复。测试环境的模拟故障不等于生产故障验证。

这四条路径是未来目标，**当前只完成了市场和 P1 资产的部分环节**；按 [ROADMAP](ROADMAP.md) 逐条补齐。

## 3. 已实现的基线与不可破坏规则

- Better Auth 独立登录；有创建权限的员工可登记现有 Web 应用、提交审核。申请人不能自批。员工市场只读 **LISTED 且已有批准快照**的内容；上架更新待审时旧公开版本继续生效。
- 已有搜索、分类、收藏、评分、评价、讨论及管理功能；“场景找应用”目前只是关键词基线，不是已接通真实语义模型。
- P1 已有 Application 单一身份、组件/环境、负责人、GitHub 外部对象引用、资产版本/审计及生命周期维护工作台。**外部引用本身只是登记；P1-02 提供私有工作台 GitHub API 按需只读查询（代码已提交 dev，待集中验证），仍不表示 CI 通过、服务健康或目标应用已部署。**
- 市场审核与上架、应用生命周期、实际部署、运行健康为**四条不同状态轴**。当前资产权限及退役等不变量详见 [ASSETS](ASSETS.md)。
- 门户可见性不等于实际目标应用使用权限；服务端必须验证身份、账号状态、资源归属和操作权限，不能通过前端隐藏按钮代替鉴权。

## 4. 下一阶段产品需求：优先业务闭环

### 4.1 P2：应用使用申请、审批与开通处理

目标：员工从应用详情发起申请，能清楚知道**谁负责、是否批准、是否真正完成开通处理**，不必先理解复杂 ITSM。

首版必须具备：
- 已登录员工对已上架应用填写理由并申请；展示“我的申请”和基本处理进展。
- 应用已有 owner 优先作为审批责任人；审批人不可批准**自己的**申请。负责人无法处理或就是申请人时，走经过授权的管理员替代处理路径，不能自动批准。
- 审批人查看待办，明确通过/驳回并可填写原因；申请者得到站内状态反馈。服务端拒绝越权和重复处理。
- **审批决策与实际使用权开通分开记录**。审批通过后可进入“待开通”；首版可由有权维护者**人工登记已完成处理**，标明“人工记录、目标系统未验证”。不虚构 SSO/IAM API 或真实开通成功。未来支持目标应用 API 接入后再独立记录验证结果。
- 不能假定平台目前知道用户是否已经具有目标应用权限；未连接授权源时显示未知，并提供访问应用或申请入口。

首轮不做：通用 BPM 设计器、多级/会签配置、企业 IAM 自动开通、复杂期限与撤权机制、各种通知渠道。需注意：批准、开通、撤销/过期是不同概念，后续增量处理而非套一个万能 status。

**主流程完成标志**：员工申请 → 非本人授权审批人处理 → 员工看到审批结果 → 有权人员登记人工开通处理 → 员工看到“人工登记”的处理结果；越权审批必须被拒。详细实现可由 Work 在当前领域模型上选最简单的事务/待办方案。

### 4.2 P1 补充：让登记的 GitHub 资产真正有用

下一批读取已登记 GitHub repo/workflow 的**真实只读数据**：最近提交、PR、流水线执行结果和更新时间，关联到对应 Application/Component/Environment 并能跳转专业页面。

优先使用 GitHub API，起步可按需查询/短缓存，不强制先建 Webhook、事件总线或统一集成框架。仅接入明确允许的资源；私有仓库凭据和运维细节按服务端权限隔离。

外部数据必须注明来源/时间，失败或未接入显示 UNKNOWN/STALE；**构建成功不等于已部署或健康**。不要把“新增更多资产表字段”当成完成这个目标。

### 4.3 P3：需求中心是“需求到交付的入口”，不是论坛

员工可以提交新功能、现有应用改进、缺陷和新应用需求；可关联应用、讨论、建议合并重复需求、认领及查看状态与处理结果。

首期建议保留：需求标题/问题描述、类型、提出人、关联应用（可空）、处理状态、负责人、交付关联（代码 PR/Commit 与门户发布记录；不以 GitHub Issue 管理需求）和结论。**需求对象 ≠ 研发执行任务 ≠ AI Worker 任务**，不能强行共用状态机。

与现有功能的连接：
- 应用详情的评论/反馈可**人工转成需求**并保留来源链接，不自动把全部评论转入需求池。
- 搜索没有匹配应用时提示提交需求；已有近似应用时可提关联改进，而不是重复创建应用。
- 需求、评论、负责人、审批及状态均保留在门户数据库；GitHub 只保存代码和 PR，Actions 暂时执行 CI/镜像构建。允许关联代码 PR 用于审查追溯，但不需要也不应自动创建 GitHub Issue。
- AI 可先只做需求归纳、相似需求提示和初步实现建议，由人确认合并/认领，不应自动关闭或直接开发未经确认的需求。

### 4.4 P3：真正的 AI 应用发现（可独立于复杂 Agent 平台）

在**已批准上架数据**中检索，按用户意图回答候选应用及依据；能辨别“已有应用”“需要申请”“改进现有应用”“需要新建应用”四种后续行动。

先用真实的查询样例评估关键词基线与语义检索增益，再决定 Embedding、向量索引、LLM 重排等实现，不为了使用 AI 引入无实际收益的复杂栈。回答不可引用未上架、未授权的私有资产；证据不足说明不确定/无匹配。推荐不应臆断员工是否拥有目标系统访问权。

### 4.5 P4：运维 L1 与 AI 只读诊断

先接入真实部署/运行状态与告警，形成**应用 → 组件 → 环境 → 提交/流水线 → 实际部署 → 健康/告警**的可追溯关联。以第三方专业系统为权威来源，在门户展示摘要、采集时间、错误或未知状态及深链；不在门户重建 Grafana 或 Jenkins。

一旦具备真实证据，可**提前试做 AI 只读诊断**：汇集有权限访问的监控、近期变更及流水线结果，提供可能原因、证据链接与人工排查建议。无执行权、不自动修复、不给不可信日志指令提权。可先在隔离 OrbStack 实验服务上验证。

后续按频率与风险增加受控 L2：预定义动作、策略许可/人工批准、执行回执、健康恢复验证和回滚；专业 L3 保留原系统入口。

### 4.6 P5–P8：在真实场景中渐进建设 AI 执行

- **P5**：从一个真实低风险长任务 PoC 抽取持久化执行、人工待办、暂停/恢复、审计及权限策略；不预选通用 Temporal/LangGraph/Agent SDK 全套架构。
- **P6**：门户需求 → 受限 AI 编码 → PR → CI → 测试环境验证。可先复用已有专业 Coding Agent；人工可主动接管、修改分支、再交回 AI，恢复时必须重读实际 SHA 和状态。
- **P7**：真实告警 → AI 辅助诊断 → 受控修复或人工处理 → 恢复校验；AI 和人工可以调用**同一个受控动作**，但审批、策略、运维状态机独立。
- **P8**：AI 创建新应用与更高自治。优先考虑标准项目模板 + AI 填业务代码，不要求 AI 从零发明基础设施；需要 P6/P7 可靠性证据。

**重要区分**：可复用身份、资产关联、待办、审计、策略和工具接口，但**使用申请、需求、部署、故障事件、长任务不能合并成一个泛化万能工作流**。

## 5. 暂缓内容与产品评估方式

**暂缓**：Agent/工作流市场、独立论坛、泛化流程设计器、复杂治理评分引擎、重造 Git/CI/监控/日志平台、过早微服务化。未来可借鉴 Backstage 模板、Port 受控操作、Compass/Cortex 软件目录、Jira 服务申请与需求关联、Coding Agent、AI SRE 的思路，**不按竞品功能列表照搬**。

每完成一个主要业务批次，只做一次简短评估：员工是否完成任务；流程还需跳到哪里；数据是否来自真实系统；哪些步骤值得由 AI 辅助；实现/维护成本是否划算。将缺口分为“阻塞主流程 / 下阶段有价值 / 暂缓”。不要为每轮生成多份报告，证据与改进建议优先记录在门户需求与发布记录；代码变更可关联 PR。

建议关注三个平台自身指标：**员工需求得到解决的比例、有效需求从提交到可用结果的时长、定位应用负责人/最近变更/故障依据的耗时**。这些是门户流程指标，不涉及目标业务应用经营数据。
## P4 当前实现状态（2026-10-14）

门户不变，AI DevOps 仅位于应用私有维护页。dev 已编码：受控 GitHub Actions/GHCR Digest → GitOps PR → OrbStack Kubernetes 的 Argo CD/Argo Rollouts 蓝绿策略、Argo 同步与健康只读、Prometheus/Loki 证据、Ollama 只读诊断。实验 Mac 配置与真实 CI/切流/回滚尚未验收，详见 TEMP_P4_MAC_SETUP.md。现有 P3 需求中心暂停。无需自建 Code RAG 或金丝雀发布引擎。

## 2026-10-15 草稿回收与测试数据治理

- 初始未提交审核的应用，允许负责人从设置页确认后删除；托管应用预留的两个环境/端口及初始 GitHub 资产引用必须在一次数据库事务里完成释放。审核过的应用不能因新增 DRAFT 版本就被误删。
- 上线后应用涉及员工使用申请、需求、审计和部署事实，需另做退役/解绑流程，**不能由普通删除草稿操作级联清空**。
- 内置的六个 example.com 假市场应用 Seed 退役。历史数据使用只针对原种子账号和六个精确签名的命令进行备份后清理；不删除测试账号或任何真实应用。

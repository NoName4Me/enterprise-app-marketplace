# 已确认的产品决策

此文件记录产品方向的**已确认决策**。首轮试行技术选型另见 [ADR-001](ADR-001-technical-baseline.md)；框架/数据库方案属于实现基线，不等于业务方已承诺长期绑定某一技术。

| 编号 | 决策 | 当前处理 |
| --- | --- | --- |
| PD-001 | 产品定位是企业内部应用市场，具有推荐、评分、社区与 AI 应用发现等能力，而非普通企业导航门户 | 生效 |
| PD-002 | 长期既支持登记已有应用，也考虑平台内创建应用；**先做登记已有应用** | 生效 |
| PD-003 | 长期扩展为更广义的应用类型；**第一阶段只支持 Web 应用** | 生效 |
| PD-004 | 第一版已上架应用对所有已登录员工可见，后续再考虑可见范围控制 | 生效 |
| PD-005 | 已上架应用更新需要重新审核，审核中**旧版本继续对外生效** | 生效 |
| PD-006 | 社区长期包含应用讨论与独立轻论坛；先做应用讨论区，后扩独立论坛 | 生效 |
| PD-007 | AI 问答仅用于发现/推荐合适的应用，不做具体应用的使用答疑 | 生效 |
| PD-008 | 第一版使用独立用户系统，不依赖企业 SSO | 生效 |
| PD-009 | 代码和项目文档在公开 GitHub 仓库维护，以 `master` 为主分支 | 生效 |

## 草案中的建议（尚非最终产品决策）

- 一个应用同时最多一条待审核申请；
- 登录用户范围、账号开通及管理员初始化流程；
- 收藏、榜单和访问统计的业务口径；
- 每个用户一条当前评分的实现及删除策略；
- 审核管理中是否支持撤回、管理员修改申请、联合维护者等。

这些规则可以作为进一步设计的起点，但应明确标注为待确认或设计假设。

## 决策变更原则

- 因业务需求改变而调整：更新决策记录并注明新原因。
- 因技术实现限制而调整：先报告权衡，不得用技术便利反向改写已确认的业务约束。
- 不对未来扩展能力过度设计。

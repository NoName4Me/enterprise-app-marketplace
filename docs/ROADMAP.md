## 阶段 1：从零到一的最小可运行闭环（已完成实现与 CI/E2E 验收；生产安全不在此验收内）

登录 → 应用草稿 → 提交审核 → 管理员通过/驳回 → 上架列表与详情 → 访问 Web 应用。

- [x] 确保未上架应用不会通过公开 API/页面泄露。
- [x] 权限不能只做前端按钮隐藏；服务端必须独立校验。
- [x] 测试覆盖至少正常、拒绝、越权与关键状态转换。
- [x] 保留开发环境的部署/运行可复现步骤；正式生产部署尚未执行。

## 阶段 2：可靠的内容更新与市场基础能力

- 已上架应用更新独立复审，旧版本持续有效。
- 应用分类、搜索、收藏、基础推荐与排序。
- 审核/变更记录、边界用例、日志与异常处理。
- 视实际需要添加最小 CI 检查。

## 阶段 3：评价和应用讨论

- 单用户有效评分、文字评价、发布者回复。
- 应用讨论帖和回复，基础内容治理。
- 独立论坛暂不包含在本阶段。

## 阶段 4：AI 智能找应用

- 准备覆盖不同部门需求、模糊提问、无结果、相似应用及未上架数据的评测样本。
- 先实现可衡量的简单基线，再决定是否需要向量检索、重排、LLM 或其他机制。
- 验证推荐真实性、匹配质量、理由可追溯、延迟及调用成本。
- 严格使用已上架应用元信息，不让模型决定真实权限或发布状态。

## 阶段 5：交付、部署和复盘（CI Docker 交付已验证；真实部署与安全阻断仍未完成）

- 安全与配置检查；不提交真实用户数据、密钥及生产环境变量。
- 可复现构建、部署、迁移、备份与基础可观测性。
- 结合实际部署能力评估 Sites 或其他托管方案，技术选型时验证兼容性。
- 总结 AI 从零到一的任务拆解、上下文管理、代码评审、测试和回退实践。

## AI Native 协作规则（暂行）

1. Chat 中完成需求权衡、重要架构决策和结果复盘。
2. GitHub 是实现与文档的事实来源；实际代码和配置变更可通过 PR 评审。
3. 工程任务要包含目标、范围、明确的禁止事项和可验证的完成标准。
4. AI 可完成大部分编码、测试和故障定位，但验收要独立于 AI 自己生成的断言。
5. 优先小批量垂直闭环，不一次性生成整个产品。
6. 对教程、示例和 AI 建议进行独立工程审查，不默认视为最佳实践。

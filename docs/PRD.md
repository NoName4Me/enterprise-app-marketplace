# 产品需求文档（PRD）

- 产品：企业内部应用市场（Enterprise App Marketplace）
- 版本：v0.1 草案
- 状态：已汇集对话中确认的产品边界；尚待技术方案、具体页面和验收用例细化
- 范围：第一阶段的 Web 应用市场

## 1. 背景与目标

为企业员工建立内部应用发现和交流平台。拥有创建权限的员工可登记已开发完成的应用，经管理员审批后向全体已登录员工展示。平台具有类似 App Store 的应用推荐、分类搜索、评分评价和社区互动，并通过 AI 自然语言理解员工需求，帮助找到匹配的应用。

当前平台管理的是**应用目录及其发布流程**，不是目标 Web 应用的开发、部署或运行平台。

### 目标用户

| 用户 | 主要目标 |
| --- | --- |
| 普通员工 | 找到并访问适合工作的应用；收藏、评价、参与讨论 |
| 获得创建权限的员工 | 登记、提交、维护自己负责的应用并回复反馈 |
| 平台管理员 | 管理账号和创建权限、审核应用及更新、维护市场秩序 |

创建权限是一项能力授权，不强制建模为独立身份；发布者同时也是普通员工。

## 2. 第一阶段的功能

### 2.1 账号与权限

- 独立用户系统：登录、退出、账号和角色/权限管理。
- 管理员可授予或撤回员工的应用创建权限。
- 普通员工不自动拥有应用创建权限。
- 首版应用市场仅面向已登录员工。
- 账号开通、密码重置及会话策略将在技术设计阶段进一步确定。

### 2.2 应用登记和上架

- 仅支持已有 **Web 应用** 的登记，包括名称、简介、详细描述、图标、分类、访问地址等元信息（字段及校验待设计）。
- 有创建权限的员工可创建/编辑草稿、提交审核，查看申请及审核结果。
- 管理员可审核通过或驳回，驳回必须写明原因。
- 通过后应用进入公开市场；驳回后申请人可以修改并重新提交。
- 支持下架及保留必要操作、审核历史。
- 同一应用同时最多一份待审核申请（首版暂定的简化约束）。

### 2.3 已上架应用更新

- 修改已上架应用的登记信息，不能直接更改线上可见数据。
- 更新提交后形成独立审核申请/快照，管理员可查看差异。
- 审核中旧版本继续展示和提供原访问地址。
- 审核通过后才切换为新版本；驳回时线上旧版本不受影响。
- 审核快照提交后不允许直接修改；需要撤回或驳回后重新提交的行为需在详细设计中明确。
- 此处的“版本”是**应用市场登记内容版本**，不指目标应用的部署版本。

### 2.4 应用市场与发现

- 首页、分类列表、关键词搜索、应用详情和访问入口。
- 收藏、最新上架、热门应用、评分排行、人工推荐。
- 榜单排序、访问量统计口径以及人工推荐维护流程尚待细化。
- 第一阶段**所有已上架应用对所有已登录员工可见**，无部门、用户组或个人可见范围配置。
- 草稿、待审、驳回和已下架内容不能进入普通员工公开搜索、榜单或推荐结果；拥有相应管理权限的人可在管理端查看。
- 门户可见性不代表目标 Web 应用实际授予使用权限；首版不提供跨应用 SSO。

### 2.5 评分、评价与讨论

- 每个员工对每个应用最多一个当前有效的 1–5 星评分，可以修改。
- 员工可留下文字评价、编辑自身评价；应用负责人可以回复评价。
- 应用详情页设讨论区：发表讨论、回复、分享使用经验、反馈问题。
- 评分/评价与讨论帖为两类不同的业务对象。
- 管理员具有基本内容治理能力；发布者不能任意删除负面反馈。
- 评论删除、举报、屏蔽、评分统计等规则留待详细设计。

### 2.6 AI 智能应用发现

- 员工使用自然语言描述场景或能力要求，AI 返回适合的已上架应用候选。
- 说明推荐原因以及能确认的能力、不满足或不确定的需求；有必要时可简短追问。
- 若无充分匹配的应用，应明确说明，不能编造应用或功能。
- 推荐所依赖的应用信息需来自已批准的当前公开版本。
- 与传统搜索共用真实应用目录，但不预设检索、重排或 LLM 技术实现；先设计评测集并比较简单基线。
- **不提供**某个应用的使用教程、操作答疑或应用内代执行。

## 3. 首个工程闭环（不等于第一阶段全部功能）

用户登录 → 获得应用创建权限 → 创建应用草稿 → 提交审核 → 管理员批准 → 应用上架 → 员工搜索/查看/访问。

在该闭环稳定后再逐步实现更新复审、收藏与反馈、推荐、AI 智能发现等功能。每个增量独立验收。

## 4. 关键验收情景（业务级）

1. 无创建权限的员工不能创建或提交应用；有权限员工可以。
2. 尚未审核通过的新应用，不能通过公开列表、搜索或直接公开详情入口看到。
3. 管理员通过审核后，其他已登录员工能够发现应用并访问登记地址。
4. 更新申请待审或被驳回时，员工仍看到旧版本和旧地址；批准后才看到新版本。
5. 同一员工修改评分不会产生第二条有效评分。
6. 普通员工可以交流，应用发布者可回复；内容治理有独立管理员能力。
7. AI 不返回未上架或不存在的应用；证据不足时承认不确定或无匹配结果。

验收场景需要在实现前转换为可执行的测试和具有样本数据的评估案例。

## 5. 非目标与后续发展方向

**本阶段不做**：
- 内置低代码、AI 生成应用、应用代码托管及运行环境；
- 桌面客户端、移动 App、AI Agent、自动化工作流类型的应用上架；
- 细粒度应用可见范围控制；
- 企业 SSO 和统一应用内授权；
- 独立轻论坛；
- 应用操作知识库与 AI 使用答疑。

**长期方向**（不形成首版工程承诺）：
- 更广义的应用类型及平台内应用创建；
- 独立轻论坛、需求征集与跨应用交流；
- 企业身份集成、应用范围控制及更丰富的推荐能力。

## 6. 待明确的问题

这些事项尚未由产品负责人最终确认，开发过程中不得将建议当作既定事实：

- 员工账号的开通方式、管理员初始化方式、密码策略；
- 发布者是否允许多人共同维护同一应用；
- 应用分类管理、重复地址/重复应用策略；
- 应用下架的触发权限和恢复流程；
- 收藏/榜单/访问量的统计口径；
- 评价与讨论的审核、举报和删除规则；
- AI 推荐质量指标、失败处理和模型成本约束；
- 首版运行环境、数据持久化及部署选择。

## 7. 变更控制

以已确认的产品决策记录为边界。重要范围变更优先更新本文和对应决策，再拆分实现任务；技术方案由独立设计文档记录。任何生成式 AI 的实现输出都需要独立验证，不因“测试通过”就视为业务正确。
